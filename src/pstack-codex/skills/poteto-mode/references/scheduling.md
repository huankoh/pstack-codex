# Codex wakeups for long-running playbooks

When a playbook requires a future `/loop` wakeup, use the host's native recurring automation or heartbeat capability, with that playbook's existing cadence, event predicate, and audit prompt. In Codex desktop, use the app automation tool; retain the current thread for heartbeat follow-ups. A live PR or CI watcher can supply event updates while this turn remains active. Keep the playbook's time-based fallback. Re-arm after the specified push waves and verdicts. A shell process or a sleep in the current turn does not establish future execution after the turn ends. If this host cannot schedule the required wakeup, report the affected monitoring step as unavailable; do not claim that it will keep watching.


Keep the schedule tied to this workflow. Before creating one, inspect the host's existing automations for this chat and objective; reuse a matching schedule. Retain its returned identity in the workflow's standing notes. Re-arming updates that schedule with the same playbook cadence, predicate and prompt; it does not create another heartbeat. Include the workflow's existing stop conditions in the scheduled prompt, and check whether the workflow has completed or is on hold before a wakeup performs work.

When the playbook's completion predicate is met, the user stops the workflow, or the playbook reaches a terminal dead end, stop its watcher and pause or delete its recurring automation through the host's automation controls. Confirm the schedule is inactive before reporting monitoring stopped. On a temporary operator hold, pause it and resume only when the operator releases the hold. A plateau, ordinary retriable failure, or unanswered status question is not a new stop condition. End only this workflow's schedule; preserve unrelated automations. If the host cannot confirm cancellation, report that future wakeups may still occur rather than claiming the loop has stopped.
